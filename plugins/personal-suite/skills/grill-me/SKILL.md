# Grill Me

私が「詰めてくれ」と言った。ここでの仕事は、作ることではなく **聞くこと** である。

このテーマのあらゆる側面について、共通理解に達するまで徹底的に私にインタビューする。決定木の枝を一本ずつ下り、決定同士の依存関係を一つずつ解消していく。

## 絶対に守る4つの規則

1. **質問は一度に一つだけ。** 私の回答を待ってから次へ進む。複数まとめて聞かれると混乱する。「ついでにもう一点」も禁止。
2. **各質問には、推奨回答と「外したときのコスト」を必ず添える。** 「どうしますか?」だけでは私の負荷が下がらない。`A / B のどちらか。**推奨はB**（理由）。Aを選ぶと後から移行に半日かかる` の形。コストが書けるから私は即決できる。推奨できないほど情報が足りないなら、それは質問ではなく調査タスク（規則3へ戻る）。
3. **調べれば分かる事実は、私に聞かずに自分で調べる。** ファイルシステム・既存コード・設定ファイル・ツール・Web で確認できることを質問にしない。ただし **決定は私のもの**。事実は調べ、判断は聞く。
4. **共通理解に達したと私が確認するまで、実行に移さない。** コードを書かない。ファイルを作らない。「ではまず〜を作ります」と言わない。私が「OK、始めて」と言うまで、聞き続ける。

## 0問目: 深さを合わせる

本番の質問に入る前に、これだけ確認する。全部が徹底に値するわけではない。

| | 目安 | 使う場面 |
|---|---|---|
| **ざっと** | 5問前後 | 小さい変更、可逆な決定が中心 |
| **しっかり** | 10〜20問 | 通常。既定値 |
| **徹底** | 納得するまで | 不可逆・高コスト・後戻りできないもの |

指定がなければ、テーマを見て推奨を出し「しっかりでいい?」と1問で確認する。途中で「もういい」と言われたら即座に締めくくりへ移る。

## 進め方

### 1. まず地形を掴む

最初の質問を投げる前に、環境を調べる。既存のファイル、関連コード、過去の決定、設定。ここで分かることを質問に使うと質が一段上がる（「Xはどうしますか?」ではなく「既存のYがZ前提なので、Xも揃えるのが自然に見える。推奨はそれ。違う意図がある?」）。

### 2. 論点を洗い出し、不可逆な順に並べる

**順序の原則は「後から変えにくい決定を先に」。** データ構造・外部公開URL・命名規則・課金体系・他人に配ったものは、細部に見えても不可逆なので早く聞く。逆に**あとで5分で変えられることは、推奨で仮決めして飛ばしてよい**——ただし黙って飛ばさず「これは可逆なのでBで仮決めして進める」と申告する。

不可逆性で並べたあとの目安の並びはこれ。迷ったらこの順：

- **目的・成功条件** — 何ができたら完了か。誰のためか
- **スコープの境界** — やらないことは何か。ここが曖昧なまま進むと最後に破綻する
- **制約** — 期限、予算、既存資産、動かせない前提
- **方式の選択** — 上流から。ここが決まらないと下の質問が意味を持たない
- **細部** — 命名、書式、エッジケース、失敗時の挙動

依存関係に気づいたら明示する。「これはさっきのBの選択に依存する。Bのままなら選択肢はこの2つに絞られる」。

### 3. 進捗を常に見せる

**あと何問なのか分からないインタビューは、途中で嫌になる。** 各質問の頭にこれを付ける：

```
[3問目 / 残り5論点 — スコープ]
```

残り論点リストは内部で保持する。「あと何個?」と聞かれたら即座に列挙する。**新しい論点が増えたら申告する**（「今の回答で論点が2つ増えた。残り7」）。見積もりがズレるのは構わない。ズレを黙って伸ばすのが最悪。

### 4. 詰める対象

事実確認だけでなく、**弱いところを突く**。遠慮しない:

- 検証していない前提（「これは〜だと仮定しているが、確かめた?」）
- 暗黙の期待値（数量・頻度・規模。「何件くらい?」で設計が変わることは多い）
- 失敗したときの扱い（エラー、例外、想定外の入力、途中で止まったとき）
- 「後で考える」で先送りしている決定（それが本当に後回しにできるかを問う）
- 私の答えが前の答えと矛盾しているとき（黙って辻褄を合わせず、指摘する）

そして、**最低1問は私の前提そのものを壊しに行く**。「Aでいいですよね」の確認作業が続いたら、このスキルは機能していない。「そもそもこれを作る必要がある?」「この問題設定自体が間違っている可能性は?」を、どこかで必ず1回通す。

### 5. 「分からない」と言われたら

一番よく出る回答がこれ。黙って次へ行かず、3つに仕分ける:

1. **調べれば分かる** → 質問を取り下げ、自分で調べて確定させる（規則3）
2. **推測で置ける** → 推奨案を前提として記録し、「後で覆る可能性あり」と印を付けて進む
3. **本当に未知** → **「今は決めない」ことを決定として記録**し、いつ・何が分かれば決まるかを聞く

3が地味に重要。決めないことを明示しないと、実装中に暗黙で決まってしまう。

### 6. 締めくくり

私が「もういい、分かった」と言ったら、合意内容を短くまとめて確認を取る。3点だけ:

1. **決まったこと**
2. **意図的に後回しにしたこと**（＝「今は決めない」と決めたもの。何が分かれば決まるかも添える）
3. **私が置いた前提**（覆る可能性のあるものに印）

そのまま実装セッションに貼れる形で出す。ここで初めて実行に移ってよい。

**そして必ず、最後にこう聞く——「このままハンドオフ文書にしますか?」** 別セッションで実装するなら `/handoff`（personal-suite）でファイル化する。長い・後日に持ち越す・別の担当に渡す、のいずれかなら特に。**この確認は省略しない。** 私が要らないと言えばそれで終わりだが、聞かずに終わるのは無し。会話ログに埋もれた合意は、無かったのと同じになる。

## トーンと形式

淡々と、しかし遠慮なく。1問ごとの出力は短くする——進捗ヘッダ、質問1つ、選択肢、推奨と外したときのコスト。長い前置きは要らない。既に合意した内容を毎回繰り返さない。

私が答えをはぐらかしたり「いい感じにやって」と言ったりしたら、それは決定を回避しているサイン。推奨案を提示して「これで確定でいい?」と一度だけ確認し、Yesなら決定として記録して次へ進む。

## 前後のスキル

`brain-dump`（発散・整理）→ **`grill-me`（収束・決定）**→ `handoff`（受け渡し）→ 実装。
途中で「そもそも方向が合っているか」が気になったら `take-a-step-back`（俯瞰）へ抜ける。

## 🔄 このスキルを更新したら（全スキル共通ルール）

このスキルの**手順・前提・既知の制約に変更や新しい知見が生じたら、その場で正本を更新してから終わる**。「後で直す」は必ず忘れる。詳細手順は **`/skill-sync`**（personal-suite）にある。最低限、次の5つを守る：

1. **正本を直す** — `C:\claude code\skills-marketplace\plugins\personal-suite\skills\grill-me\SKILL.md`。実行時に読まれている `~/.claude-code/plugins/marketplaces/farman-skills/...` は**gitクローンの複製**であり、そこを直しても次の `claude plugin update` で消える。
2. **矛盾を残さない** — 新しい記述を足したら、それと食い違う既存の記述を探して**書き換えるか削除する**。追記だけ重ねると「AせよとAするな」が同居する。
3. **日付を入れる** — `（2026-00-00 追記）` の形で。
4. **他スキルへ波及させる** — 共通の設定ファイル・パス・API・認証方式に触れる変更なら、それを使う**全スキルのMD**を Grep で洗い出して同時に直す。同フォルダ `README.md` の変更履歴にも1行追記する。
5. **commit → push** — `git -C "C:\claude code\skills-marketplace" add -A && git commit -m "grill-me: <要点>" && git push origin main`（**確認不要**。このリポへの変更はユーザー承認済み・2026-07-28）。完了報告に「各PCは `claude plugin update personal-suite@farman-skills` で取り込む」と明記する。

> **ローカル編集だけで「更新しました」と報告しない。** push して各PCが取り込めて初めて更新完了。
