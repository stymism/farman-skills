# 有機JAS 栽培履歴の作成

作業日誌（Googleスプレッドシート）と圃場台帳（Excel）から、**1圃場=1シート**の栽培履歴を作り、
地名ごとのブックにまとめて提出する。年に一度の定例業務。

このスキルの価値は手順そのものより **「黙って取りこぼす罠」を全部潰してあること** にある。
過去に実際に数量が丸ごと欠落した事故が複数あるので、下の「5つの罠」を必ず読んでから着手すること。

## 最初に確定させること

着手前にユーザーへ確認する。ここが曖昧なまま作ると全シート作り直しになる。

1. **対象年度と期間**（例: 2025/1/1〜12/31。年度途中まで、もあり得る）
2. **対象圃場** — 圃場台帳で**取り消し線が引かれた行は作成済み**を意味する。除外する
3. **肥料の使用量を載せるか** — 直近の運用では**種類のみ記載し、使用量は一切載せない**
4. **耕作履歴がない圃場の扱い** — 「休耕・不作付」として1シート作る（提出物の欠落を防ぐ）
5. **栽培圃場でない台帳行**（集出荷場用地など）を除外するか

## 手順

### 1. 作業日誌を xlsx でダウンロードしてもらう

**スプレッドシートから直接読むのは禁止。** 必ずユーザーに
「ファイル → ダウンロード → Microsoft Excel(.xlsx)」で落としてもらい、そのパスを受け取る。
理由は「罠1」を参照。

### 1.5 実行環境を見分ける

**Cowork（クラウド）の場合はローカルのフォルダが見えない。** 先に環境を確かめること。

| | ローカル Claude Code | Cowork |
|---|---|---|
| ファイルの渡し方 | 設定ファイルにパスを書く | **4つともアップロードしてもらう** |
| 出力先 | 設定の `outputDir` | 出力用ディレクトリ → ユーザーがダウンロード |
| 設定ファイル | `~/.farman/cultivation-record.json` | これもアップロードしてもらう |

Coworkでは `--daily-log` `--ledger` `--template` `--out-dir` でパスを上書きする（下記）。

### 2. 設定ファイルを用意する

`~/.farman/cultivation-record.json`。無ければ `scripts/config.example.json` をコピーして作る。
**スプレッドシートID・個人名・地番はここにだけ書く。リポジトリには絶対にコミットしない。**

### 3. 抽出 → 確認 → 生成

```bash
python scripts/extract.py --config ~/.farman/cultivation-record.json -o records.json
python scripts/build.py   --config ~/.farman/cultivation-record.json -r records.json
```

**Coworkの場合**は、アップロードされた4ファイル（作業日誌・圃場台帳・ひな形・設定ファイル）の
実際のパスを引数で渡す。設定ファイル内のパスは使わない。

```bash
python scripts/extract.py --config <設定.json> -o records.json --daily-log <日誌.xlsx> --ledger <台帳.xlsx>
python scripts/build.py --config <設定.json> -r records.json --ledger <台帳.xlsx> --template <ひな形.xlsx> --out-dir <出力先>
```

`openpyxl` が無ければ `pip install openpyxl` を先に実行する。

`extract.py` は「未解釈が残った圃場セル」を出力する。**ここが0件でなければ先へ進まない。**
残っていたら `nonFieldLabels` か `aliases` に足す（`references/field-codes.md`）。

`build.py` は圃場別の作業件数・苗種数・数量不明数と、履歴から除外した事務作業の一覧を出す。
件数が明らかに少ない圃場があれば、圃場コードの取りこぼしを疑う。

### 4. 目視確認

LibreOfficeでPDF化して**必ず1シートは目で見る**。特に作業件数が最多の圃場と休耕シート。

```bash
soffice --headless --convert-to pdf --outdir render "出力.xlsx"
```

### 5. 納品

OneDriveの所定フォルダへ `_v1.0` 付きで保存する。修正のたびに番号を上げ、**上書きしない**。

## 5つの罠（すべて実際に踏んだ）

### 罠1: gvizやCSVエクスポートはフィルタを反映して行が消える

日誌のタブに絞り込みが残っていると、`gviz/tq?tqx=out:csv` は**表示中の行しか返さない**。
ある年は4月が2行・7月が8行しか取れず、実際は各44〜63行あった。
Drive APIコネクタ経由も**各タブ約45行で打ち切られる**。
→ **xlsxダウンロードだけが唯一確実**。他の経路を使ってはいけない。

### 罠2: 列位置が月によってずれる

同じ年の日誌でも、ある月から**作物以降が1列右にずれる**ことがある（列の挿入跡）。
固定列番号で読むと、空列を「作物」として読み、定植数量を丸ごと落とす。
→ `resolve_cols()` が**見出し行から実測**する。固定値を書かないこと。

古い月は圃場列の顔ぶれ自体が違う（「長沢/窪長沢/その他」だけ等）ことにも注意。

### 罠3: 数量が文字列型で入っている

合計粒の欄に `'4000'` と**文字列**で入っている行がある。数値型だけ拾うと消える。
→ `to_num()` が文字列も数値化する。

### 罠4: 1セルに複数圃場がまとめて書かれる

`C.N.O.P.R` `A DM S C N O` `ＰＴＵＲ`（全角）`N O P C A I DM T U R` のような記載がある。
区切りはドット・空白・全角空白・無しが混在。**該当する全圃場に同じ作業として展開する**。
「その他」列にも `長沢;S C K 農場周り` 形式で圃場が書かれることがあり、これも拾う。
詳細は `references/field-codes.md`。

### 罠5: データ開始行が月によって違う

見出しが2行の月と3行の月がある。`range(4, ...)` のような決め打ちは先頭行を落とす。
→ 日付セルが日付として読める行をすべてデータ行として扱う。

## 判断が必要になりやすい点

日誌は現場の記録なので、そのままでは提出資料にならない部分がある。**勝手に決めずユーザーに確認する。**

| 論点 | 過去の判断 |
|---|---|
| 常に一体で記録される2圃場（`DM` など） | 1シートに統合し、面積は台帳の合算 |
| 台帳にない略号（`GA` `GB` など） | 台帳の親圃場へ寄せる |
| 圃場でない呼称（集出荷場・施設名・「周辺」） | 除外 |
| 圃場欄に書かれた事務・出荷作業 | 履歴から除外し、除外一覧を報告する |
| 造成工事しか記録がない圃場 | 休耕扱い＋工事記録がある旨を注記 |
| 外部委託タブ | 自社圃場に該当する行だけ取り込み「(委託作業)」と注記 |
| 苗・種の数量が日誌にない | セルを塗りつぶして「不明」を明示（空欄で流さない） |

## 出力フォーマット

ひな形の書式を引き継ぐ。詳細は `references/output-format.md`。

- ヘッダー部: 圃場名／栽培面積（台帳の合算）／責任者／**苗・種の使用数（作物・品種ごと）**／肥料／使用資材／使用機械
- 苗・種は5組ずつ折り返す**可変ブロック**。品種が違えば別枠にする（ニンニク3種など）
- 数量が日誌にない枠は**クリーム色で塗る**
- 作業履歴: 月日／作物・品種／作業内容 を2ブロック並べる。作業内容から数量・希釈倍率は落とす
- A4横・1ページ幅に収め、見出し行を各ページに繰り返す

## やってはいけないこと

- **納品済みファイルをワイルドカードで削除しない。** `rm *_v1.3.xlsx` の類は、
  ユーザーが手修正した版まで巻き込む。Git Bashの `rm` はごみ箱を経由せず**復旧できない**。
  旧版の削除は必ず1ファイルずつ、ユーザーの明示的な指示があるときだけ行う。
- スプレッドシートID・個人名・地番をSKILL.mdやスクリプトに直書きしない（設定ファイルへ）
- 「作業件数が0だから休耕」と即断しない。圃場コードの取りこぼしを先に疑う
